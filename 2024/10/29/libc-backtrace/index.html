A Definite Walk Down the Call Stack

Gilbert Bustros
2024-10-29
abi, assembly, c/c++, compiling, debugging, linux

Introduction

When a program crashes, identifying the function where it stopped is only part of the investigation. We also want to know which calls brought execution there. A backtrace shows that chain of active function calls, giving us context for investigating the failure. Understanding how function calls use the stack is the first step toward learning how to read a backtrace and understand its limitations.

In this article, we will follow a small C++ program on Linux x86-64, examining its assembly and using GDB to inspect the stack as functions call one another. We will then use glibc’s backtrace() to capture the call chain from within the program, connecting its output to the stack frames we inspected.

Prerequisites

Basic familiarity with C or C++, including functions, local variables, pointers, and hexadecimal numbers, is assumed. Some experience with compiling programs and running commands in a Linux terminal will also be helpful. The assembly instructions and GDB commands needed for the walkthrough are explained as they are introduced.

The references linked throughout the article provide additional information that can help fill in most of the knowledge gaps needed to understand the topics covered here.

The commands below assume an x86-64 Linux system with glibc, g++, GDB, and GNU Binutils installed. The examples were checked with GCC 15.2, GDB 17.1, GNU Binutils 2.46, and glibc 2.43 on Ubuntu 26.04.

Virtual Memory and the Stack

Before examining individual stack frames, we need to place the stack within the program’s memory layout. On Linux, each process has a virtual address space. In other words, the addresses used by the program are translated by the system to physical memory. This address space contains mappings for executable code, data, shared libraries, and the stack. These regions do not need to occupy adjacent locations in physical memory. Linux virtual memory overview, Linux process memory mappings

Each thread has its own stack, where data associated with its active function calls is stored. This data includes saved registers, return addresses, and local variables that need stack storage. On x86-64, it grows toward lower virtual addresses. The address of the current top of the stack is held in the stack pointer. When more stack space is reserved, the stack pointer is moved to a smaller address. When that space is released, it is moved back toward a larger address. A value is placed on the stack by push, while the value at the top is read into a destination by pop and its stack space is released. When a 64 bit register is pushed or popped, the stack pointer is decreased or increased by 8 bytes, respectively. A return address is also placed on the stack by call and removed by ret. Space can be reserved without storing a value by subtracting from the stack pointer, and released by adding to it. For example, reserving 32 bytes from a stack pointer of 0x1000 moves it to 0x0fe0. This growth direction follows the architecture’s stack operations. The virtual address range for the main thread’s stack is established by the Linux kernel when the program is started. Intel architecture manual, Volume 1, Section 6.2, Linux process memory mappings

The Stack Pointer

On x86-64, the rsp register holds the stack pointer. We can see how it changes in our example, where sub rsp, 0x20 reserves 32 bytes by moving the stack pointer to a lower address. Intel architecture manual, Volume 1, Section 6.2

The first command prints the stack pointer’s value. The second displays eight consecutive eight byte units of memory in hexadecimal, starting at $rsp. The addresses on the left identify memory locations. The values beside them are the contents stored there. Program Counter

The stack pointer tells us where the current stack boundary is. The program counter tells us where execution will continue. On x86-64, this role belongs to the instruction pointer register rip. When GDB pauses our program, we can inspect it to find the next instruction to execute. GDB also provides the architecture independent name $pc for this register. GDB registers

The first command prints the instruction pointer’s value. The second displays the instruction at that address. GDB memory inspection

A function call connects the instruction pointer to the stack. In our example, call pushes the address of the instruction immediately following it onto the stack, then transfers execution to some_function(). This saved address is the return address, so if the function returns normally, ret takes it from the stack and transfers execution back there. In this build, the call is at 0x118b and its return address is 0x1190. These are addresses from the disassembly. The addresses shown while running in GDB may differ because the executable can be relocated when loaded. Intel architecture manual, Volume 1, Sections 6.3 and 6.5

Frame Pointers

In this build, each of our functions uses rbp as a frame pointer, which provides a stable reference for accessing data in its stack frame. At the start of some_function(), push rbp saves the caller’s frame pointer on the stack, and mov rbp, rsp establishes the new one. The following instruction, sub rsp, 0x20, reserves stack space while leaving rbp unchanged. This lets the function access its local variable at [rbp-0x4]. Intel architecture manual, Volume 1, Section 6.2.4.1

Frame pointers are a compiler choice. GCC can omit them during optimization. We explicitly retained them for this walkthrough with -fno-omit-frame-pointer. GCC optimization options

Once these setup instructions have executed, rbp points to the saved value of the caller’s frame pointer. The return address sits eight bytes above it, at [rbp+0x8], because call pushed it before push rbp saved the frame pointer. The space reserved for this function lies below rbp, toward lower addresses. We can therefore describe this build’s frame using offsets from rbp, as shown in the following table. Intel architecture manual, Volume 1, Section 6.2

Location Contents
[rbp+0x8] Return address into main()
[rbp] Saved frame pointer of main()
[rbp-0x4] Local variable var after initialization
[rbp-0x14] Saved copy of argument in
rbp-0x20 Value of rsp after reserving stack space

This layout comes from our generated assembly. Other builds may use different offsets.

Capturing a Backtrace with glibc

So far, we have inspected the call chain from outside the program using GDB. The GNU C Library also provides backtrace(), declared in <execinfo.h>, to capture it from within the running program. The function fills a caller provided array with return addresses for the current thread and returns the number of entries written. Capturing these addresses and turning them into readable function names are separate steps. GNU C Library manual

Our manual frame pointer walk illustrates one way to recover callers. glibc’s implementation can instead use unwind metadata that describes how to recover the caller’s registers and return address. On the tested x86-64 system, it uses the unwinder’s _Unwind_Backtrace() interface. Omitting frame pointers therefore does not necessarily prevent a backtrace when suitable unwind information is available. We retain frame pointers here to make the manual inspection straightforward. glibc backtrace implementation

Save this version as backtrace.cpp. Before calling std::abort(), it captures up to 32 frames and uses backtrace_symbols_fd() to write a readable representation of their addresses to standard error. Function names appear when symbol information is available. GNU C Library manual

This change alters the generated assembly and frame layout, so the offsets from our earlier walkthrough apply to the original program.

The additional -rdynamic option exposes the executable’s symbols to dynamic symbol lookup, allowing function names to appear in the output. GNU C Library manual

A backtrace reflects the active calls represented in the compiled program, so it may differ from the call structure we see in the source. Inlined functions do not have separate physical stack frames, and tail call optimization can replace a caller’s frame with its callee’s. Our array also limits the capture to 32 entries, so if backtrace() returns 32, there may be additional frames that did not fit. GNU C Library manual

When to Use backtrace()

backtrace() is useful for diagnostics during ordinary execution, such as logging an unexpected condition, investigating which functions called the current one, or reporting an error before terminating. Our example captures the trace before std::abort(), so it runs outside a signal handler. glibc documents backtrace() as thread safe, but thread safety and signal safety are different properties. GNU C Library backtraces, glibc safety concepts

A signal handler can interrupt a thread while a library operation is only partly complete. For example, if the interrupted operation holds an internal lock and the handler calls code that needs the same lock, the handler can deadlock because it cannot acquire the lock, and the interrupted code cannot resume to release it. Reentering code that is updating shared internal state can also produce inconsistent results. Functions documented as async signal safe are designed to support this execution context. Being thread safe alone does not provide that guarantee. Linux signal safety

glibc marks backtrace() as async signal unsafe because its execution can involve initialization, heap operations, dynamic loading, and locks. The Linux manual notes that the first use can load libgcc, which usually involves memory allocation. Calling it during startup can avoid that particular first use loading step, but does not establish general signal safety. backtrace_symbols() allocates its strings. backtrace_symbols_fd() avoids that allocation, but the preceding call to backtrace() remains unsafe. GNU C Library backtraces, Linux backtrace manual

Final Notes

A backtrace depends on the information needed to recover callers remaining intact. If that information is corrupted, for example by a buffer overflow or an invalid memory write, the call chain may be incomplete or impossible to reconstruct reliably.

For reliable crash reporting and stack analysis, tools like Breakpad offer additional capabilities. Breakpad’s stack walkers can use frame pointers, compiler generated unwind information, or, when other methods fail, scan stack memory for plausible return addresses. The available methods depend on the architecture and the information preserved in the dump and symbol files. Stack scanning is heuristic and can mistake unrelated values for return addresses. Breakpad stack walking documentation, Breakpad x86-64 stack walker

Conclusion

The stack holds information about active function calls, allowing the chain of callers to be reconstructed. With GDB, individual stack frames can be inspected and the call stack can be examined to understand how execution reached a particular point. With glibc’s backtrace(), that chain can also be captured from within the program and included in diagnostic output. In production, you can use a well established solution to obtain a backtrace.
